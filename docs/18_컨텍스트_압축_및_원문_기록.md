# 컨텍스트 압축과 원문 기록

모델이 보는 대화와 실행 원문을 분리한다. 원문은 순서대로 추가하는 JSONL에 남기고, 컨텍스트가 커지면 모델에 보낼 오래된 대화만 요약으로 교체한다. 요약이 원문을 덮어쓰지 않는다.

## 보존 범위

앱 지시, 사용자 입력, 모델 응답과 도구 호출, 도구 결과, 모델에 반환하는 검사 피드백을 기록한다. 검사기 subprocess stdout/stderr 전문은 별도 수집 대상이며 이 기능의 원문 대화와 동일하지 않다. 모델 응답은 보고서의 4KiB 제한 전에, 도구 결과는 64KiB/누적 1MiB 제한 전에 저장한다. compact가 켜져 있으면 모델용 도구 결과는 별도로 해결된 trigger_tokens*3/4바이트까지 전달하고 잘린 경우 원문 index를 붙인다. 보고서 도구 기록의 기존 제한은 유지한다. 원문은 Dust가 실제 받은 내용이며, 외부 도구가 반환하기 전에 이미 자른 내용은 복원하지 않는다. 모델의 비공개 reasoning도 원문 대화와 같다고 보장하지 않는다.

기본 저장소는 HOME/.dustagent/history이며 DUST_HISTORY_HOME으로 바꿀 수 있다. 매 실행·ACP 세션마다 별도 디렉터리와 transcript.jsonl을 만든다. Unix 디렉터리는0700, 파일은0600이다. 내용에는 실행 중 받은 데이터가 그대로 들어간다. 자동 삭제·원문 덮어쓰기는 하지 않는다. 레코드당 최대16MiB, 아카이브당 최대256MiB이며 초과·쓰기 실패 시 잘라서 성공하는 대신 중단한다.

## compact 정책

```json
{"compaction":{"enabled":true}}
```

기본값은 모델별 입력 예산에서 계산한다. 앱의 `context_window_tokens` 지정값이 가장 우선하며, 없으면 provider의 한도 정보를 사용한다. Codex는 `$CODEX_HOME/models_cache.json` 또는 `~/.codex/models_cache.json`에서 선택 모델의 `context_window`와 `effective_context_window_percent`를 읽는다. 캐시가 없거나 잘못됐거나 선택 모델이 없으면 한도를 모르는 것으로 처리한다. 자격증명 값은 읽거나 기록하지 않는다. 공식 OpenAI API endpoint는 소규모 정확한 모델 ID 표를 사용한다(gpt-4o-mini/gpt-4o 128000, gpt-6.1-sol 1050000). 다른 endpoint에는 이 표를 적용하지 않는다.

한도를 모르면32768토큰을 보수적인 fallback으로 사용한다. 이는 실제 서버 한도의 보장이 아니다. 로컬 모델·게이트웨이는 실제 배포 한도를 앱에 지정한다.

```json
{"compaction":{"context_window_tokens":32768}}
```

출력용·다음 도구 결과용 여유를 각각 context window의10%(최소1024토큰) 확보하고 나머지를 입력 임계값으로 삼는다. 예를 들어128000이면102400,32768이면26216이다. 이 비율은 Dust의 조정 가능한 구현 정책이며 업계 표준 수치가 아니다. `max_summary_tokens`는 입력 임계값의1/8을 자동 요약 출력 예산으로 삼는다. `max_summary_bytes`는 토큰 예산과 별개인 UTF-8 안전 상한이다. 최근 내용은 시스템 지시·필수 요청·요약·원문 안내 여유를 포함해 임계값의75% 안에 들어가는 가장 긴 최근 완료 대화 접미 구간을 보존한다. 최소 보존 범위는 시스템 지시와 첫/최신 사용자 요청, 원래 입력과 같은 사용자 메시지다. 마지막 완료 도구 묶음이 너무 크면 그 묶음 전체를 요약 대상으로 옮길 수 있다. 명시한 keep_recent_messages는 원하는 최근 메시지 수의 상한이며 완결된 묶음 경계와 크기 제한이 우선한다. 필수 지시/요청만으로도 하드 제한을 넘으면 모델 호출 전에 중단한다. 실제 요약과 안내를 포함한 최종 대화가 입력 임계값과 최대 입력 예산을 모두 통과해야 정상 모델 요청을 진행한다.

`trigger_tokens`, `keep_recent_messages`, `max_summary_tokens`, `max_summary_bytes`의 기본값0은 자동 계산을 뜻한다. `max_summary_tokens`는 trigger의1/8이며 허용 범위는128~65536이다. `max_summary_bytes`는 의미상 요약 크기 기준이 아니라 UTF-8 안전 상한이다. 자동값은 토큰 상한의8배(최대65536바이트)다. 기존 명시적 바이트 설정은 추가 안전 상한으로 계속 적용된다. 허용 범위는 context_window_tokens4096~10000000, trigger_tokens0 또는1024~1000000, 최근 메시지0 또는2~128, max_summary_bytes0 또는256~65536바이트다. OpenAI 호환 Chat Completions 응답의 prompt/completion usage와 cached_tokens, Codex Responses 완료 응답의 input/output usage와 cached_tokens를 보존한다. 응답 사용량이 있으면 요약 토큰 검증에 제공자 수치를 우선 사용한다. reasoning_tokens가 있으면 출력 사용량에서 빼서 표시 가능한 요약 출력량을 구한다. 사용량이 없으면 UTF-8 길이/3으로 근사하며, 모델 tokenizer와 정확한 사전 요청 context 계측을 보장하지 않는다.

요약은 현재 요청과 유지할 지시를 참고해 **목표·사용자 제약·완료한 작업·결정과 이유·남은 작업·실패와 원인·정확한 식별자/경로/근거 위치·불확실성**을 남긴다. 중복 관찰과 반복 도구 출력은 줄이고, 후속 작업에 필요한 정보의 보존을 우선한다. 요약 요청은 요약 출력 예상량과 여유까지 포함해 설정된 context window 안에 들어가야 한다. 첫 요청처럼 요약할 과거가 없어도 출력 여유를 뺀 최대 입력 예산을 넘으면 모델에 보내지 않고 원문을 유지하며 중단한다.

설계 근거: [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction). Dust의 범용 텍스트 요약은 provider의 비공개 reasoning까지 보존하는 전용 compact API와 동일하지 않다.

다음 모델 요청 직전의 안전한 경계에서 오래된 완료 대화를 요약한다. 활성 대화의 도구 호출·결과를 중간에서 분리하지 않는다. 앱 시스템 지시와 원래/현재 사용자 요청, 예산에 맞는 최근 완결된 도구 배치를 보존한다. 요약 요청은 도구 없이 같은 provider로 실행하며 턴·시간 예산에 포함한다. 빈 요약(공백만 있는 응답 포함)·도구 호출·너무 큰 요약·크기가 줄지 않는 요약은 교체하지 않는다. 빈 요약·크기 초과·예상치 못한 도구 호출은 기본2회 추가 재시도하며, 매 요청은 기존 턴·시간 예산에서 차감한다. 재시도는 기존 원문 대화에 실패 이유와 더 짧은 요약 목표를 전달해 다시 요약한다. 요약에 포함된 도구 호출을 실행하거나 작업 도구를 재실행하지 않는다. 실패해도 원문은 남는다.

요약 입력이 한 요청에 들어가지 않으면 오래된 대화를 JSON 참고자료로 직렬화한 뒤 연속 UTF-8 구간으로 나눠 처리한다. 필수 지시/요청, 이전 구간의 미검증 요약, 실패 피드백, 현재 구간의 JSON 이스케이프 증가량까지 실제 요청 추정치에 포함하고 요약 출력 여유를 남긴다. 참고자료와 헤더의 JSON 인코딩으로 내용에 포함된 가짜 구분자/피드백 문자열을 필드 값으로 유지한다. 구간은 긴 도구 결과나 JSON 문자열 중간에서 나뉠 수 있지만 원래 메시지의 바이트를 빼거나 도구를 재실행하지 않는다. 매 응답은 이전 미검증 요약에 다음 구간의 정보를 반영한 새 제한 크기 요약이다. 모든 구간이 끝나고 최종 교체가 하드 제한을 통과할 때까지 활성 원문/도구 묶음은 유지한다. 구간마다 재시도 허용량을 적용하고 모든 모델 호출은 동일한 턴·시간 예산을 사용한다. 중간 응답도 아카이브에 남긴다. 원문 보존과 입력 크기 제한을 보장하는 정책이며 모델 요약의 사실 누락 방지를 보장하지 않는다.

요약은 assistant 역할의 과거 참고자료로 넣으며 앱 시스템 지시로 승격하지 않는다. 완료 증거를 대신하지 않는다. 생성된 요약 응답도 별도 표시해 아카이브에 보존한다. 원문 기록 범위를 연결해 세부 내용은 내장 도구로 다시 확인할 수 있다. 보고서의 compaction 이력에서 전후 크기와 메시지 수, 원문 범위, 실제 적용한 context window·임계값·요약 상한을 확인한다.

## 실패 진단과 재시도

`max_summary_retries`는0~3이며 기본2다. 0은 실패 시 바로 중단하고, 2는 각 입력 구간의 최초 요청을 포함해 최대3번 요약을 시도한다. 한 요청에 맞는 정상 압축은 한 번만 호출하며, 큰 입력은 여러 구간을 기존 예산 안에서 처리한다. 제공자 오류·취소·시간 초과·입력 자체의 초과·압축 후 예산 초과·아카이브/색인 오류는 이 요약 검증 재시도로 숨기지 않는다.

`compactions`는 성공한 압축 목록이다. 별도 `compaction_attempts`는 성공과 실패 모두 기록한다. `turn`은 실제 시도 턴, `attempt`는 한 압축 작업 안의1부터 시작하는 시도 번호다. `status`는 `accepted`, `empty`, `oversized`, `unexpected_tool_calls`, `provider_error`, `cancelled`, `time_limit`, `input_too_large`, `non_reducing`, `directory_error`, `archive_error`로 구분한다. 요약 응답을 받으면 `summary_bytes`, `summary_tokens`, `summary_token_source`를 기록한다. source는 `provider_reported` 또는 `estimated`다. 함께 저장되는 `provider_usage`에는 제공자가 반환한 입력/출력/캐시/추론 토큰 수가 포함될 수 있다. `max_summary_tokens`가 의미상 출력 상한이며, `max_summary_bytes`는 별도의 안전 상한이다. `tool_call_count`, `elapsed_ms`, `archive_index`, `error`도 남긴다. 응답을 받지 못했다면 요약 수치와 원문 위치는 null이다. 일반 모델 호출의 토큰 사용량도 `turns[].provider_usage`에서 확인할 수 있다.

제공자가 usage를 반환하면 JSON 실행 리포트에 `token_usage` 합계가 포함된다. 일반 턴과 압축 응답별 usage를 더한 값이다. 캐시 입력은 입력 토큰의 일부이고 reasoning은 출력 토큰에 포함되므로, 이 하위 항목들을 `total_tokens`에 다시 더하지 않는다. `uncached_input_tokens`는 한 응답에서 입력과 캐시 수치가 모두 보고된 경우에만 계산하고, `responses_with_uncached_input`은 그 응답 개수다. 제공자 `total_tokens`가 없으면 입력과 출력이 모두 있는 응답에 한해 두 값을 더한다.

예를 들어 리포트에는 다음처럼 저장된다.

```json
{
  "token_usage": {
    "responses_with_usage": 3,
    "input_tokens": 8120,
    "cached_input_tokens": 6144,
    "uncached_input_tokens": 1976,
    "responses_with_uncached_input": 3,
    "output_tokens": 870,
    "reasoning_tokens": 320,
    "total_tokens": 8990
  }
}
```

`input_tokens`, `output_tokens`, `reasoning_tokens`는 제공자가 보고한 응답별 값을 합산한다. `total_tokens`는 제공자 총계가 있으면 그 값을 사용하고, 없으면 입력과 출력이 모두 보고된 응답에 한해 둘을 더한다. 일부 응답이나 세부 카운터가 누락되면 합계는 알려진 값만 더한 부분값이 될 수 있고, 한 번도 보고되지 않은 카운터는 null로 남는다. usage가 전혀 없으면 `token_usage`를 생략한다. 응답별 원본 수치는 `turns[].provider_usage`와 `compaction_attempts[].provider_usage`에 보존된다. `--report run-report.json`으로 파일에 저장한 뒤 `jq '.token_usage' run-report.json`으로 합계를 확인할 수 있다.

여러 구간을 처리하는 압축에서 attempt는 각 구간의1부터 시작하고 accepted는 그 구간의 요약 검증 통과를 뜻한다. 중간 accepted만으로 활성 대화 교체가 완료됐다고 판단하지 않는다. 실제 설치된 전체 압축은 compactions에만 기록된다.

예를 들어 usage를 주지 않는 provider의 한글 요약이9834바이트면 `summary_tokens: 3278`, `summary_token_source: estimated`로 남는다. 자동 토큰 상한3277을 넘으면 `oversized`이며 바이트 안전 상한과 별도로 판정한다. provider usage가 있으면 `provider_reported`로 표시한다. 원문 응답은 실패한 요약도 아카이브에 남긴다. 리포트에는 원문 본문을 복제하지 않는다. 외부 러너가 임시 아카이브를 지워도 상태·수치 진단은 남지만, 삭제한 전문을 리포트에서 복원할 수는 없다. 기존 리포트와 체크포인트에 새 필드가 없어도 읽을 수 있다.

## 원문 안내 색인

압축된 요약만으로는 원문에 무엇이 있는지 알기 어렵다. compact마다 원문 범위와 주제 설명, 실제 등장한 검색어·레코드 번호, 짧은 발췌를 담은 안내 목록을 만든다. 주제 설명은 이미 생성한 요약을 재사용하며 검증된 사실로 취급하지 않는다. 검색어·위치는 Rust에서 원문 문자열로 추출한다. 원문 구간에서 최대10개 위치를 고르게 선택해 발췌하고, 검색어는 최대12개를 남긴다. 도구 이름·인자에 들어 있는 URL/파일 경로도 대상이다. 원문 전체를 대표하는 완전한 의미 색인을 보장하지 않으며, 검색어 목록에 없다는 이유로 해당 내용이 원문에 없다고 판단하면 안 된다. 별도 LLM 호출은 추가하지 않는다.

목록은 `transcript.jsonl` 내부의 별도 metadata 레코드에 누적한다. 메시지 본문이 목록처럼 생겼다고 metadata로 인정하지 않는다. 목록은 원문과 동일한 권한·용량 제한·해시 체인·체크포인트 검증으로 보호한다. 재개할 때 검색어와 발췌가 지정된 원문 레코드에 실제 존재하는지도 확인한다. 각 목록의 범위는 이전 목록 이후 새로 기록된 아카이브 구간이며, 압축 과정에서 실제 제거된 메시지와 정확히 같은 집합이라고 주장하지 않는다. 직전 모델 요약 응답과 이전 색인 metadata를 새 원문의 검색어 근거로 사용하지 않는다.

컨텍스트에는 최신 목록의 짧은 안내와 전체 목록 조회 도구를 남긴다. 안내는 입력 예산에 따라256~2048바이트 이내로 제한하고 UTF-8 경계를 지킨다. 목록 전체를 매번 컨텍스트에 쌓지 않는다. 오래된 목록은 페이지 단위로 조회해 주제·검색어·원문 번호를 확인하고, `history_read`로 실제 내용을 읽는다. 색인 후보와 안내를 먼저 준비해 입력 예산을 다시 검사하고, 통과한 경우에만 metadata를 저장하고 압축된 컨텍스트를 설치한다. 예산 검사에서 거부된 후보는 다음 구간의 시작 위치를 바꾸지 않는다. 목록은 원문 발견을 돕는 것으로 완료 증거를 대신하지 않는다.

## 내장 원문 조회

- dustagent__history_directory: 현재 실행/세션의 누적 원문 안내 목록 조회. 선택적인 query로 설명·검색어·발췌를 검색하고 cursor로 이어서 조회한다. cursor는0부터 시작하는 목록 위치이며 원문 레코드 번호와 다르다. 페이지 limit은 최대10이며 응답은16KiB 이내로 제한한다. query가 있을 때 각 결과의 matched_by 배열은 description(미검증 요약 설명), keyword(원문 검색어), preview(원문 발췌) 중 일치한 항목을 알려준다. 설명 일치만으로 해당 단어가 원문에 있다고 판단하지 않는다.
- dustagent__history_search: 현재 실행/세션의 원문에 대한 대소문자 구분 문자열 검색. 쿼리는 최대256문자, 결과는 최대20개, 다음 cursor로 이어서 조회한다.
- dustagent__history_read: 1부터 시작하는 원문 index와 offset으로 조회한다. 페이지는 최대16KiB이며 다음 offset을 반환한다. offset은 원문 메시지를 JSON으로 직렬화한 문자열의 UTF-8 바이트 위치다.

도구는 파일 경로나 다른 세션 ID를 받지 않는다. 검색은 페이지별 최대1000개 레코드 또는4MiB를 검사하며, 결과가 없어도 남은 기록이 있으면 cursor를 반환한다. 조회는 잘린 보고서 문자열이 아니라 원문 아카이브를 읽는다. 원문 조회 결과는 누적 보고서 예산 소진으로 모델에게 빈 결과만 전달되는 상황을 피하도록 별도로 제한한다.

## 세션과 체크포인트

ACP 후속 prompt는 같은 세션의 원문 기록을 이어 쓴다. 다른 세션은 별도 기록을 사용한다. 체크포인트에는 압축된 활성 대화와 원문 참조를 함께 저장한다. 재개 시 앱·작업 디렉터리 바인딩과 레코드 수·해시를 검증하며, 원문이 바뀌거나 없으면 재개를 차단한다. 바인딩은 SHA-256으로 기록해 매니페스트 환경변수 값이 참조 메타데이터에 노출되지 않는다. 저장소 환경도 동일하게 유지해야 한다.

구간 요약 중 중단하면 체크포인트에는 교체 전 활성 원문과 이미 받은 요약 응답의 아카이브 참조가 남는다. 임시 구간 커서는 저장하지 않으므로 재개 시 같은 원문을 다시 요약할 수 있다. 재요약도 재개 실행의 턴·시간 예산을 사용한다.

기존 체크포인트는 새 참조가 없어도 읽을 수 있지만, 과거에 잘린 도구 결과의 전문을 되살리지는 못한다. 원문 기록과 compact는 불확실한 도구 결과의 강제 재실행을 허용하지 않는다.

## 검증

큰 마지막 완료 배치와 구간 요약 변경은 압축 단위/통합/CLI 집중35개 테스트와 포맷 검사로 검증했다. 12개 병렬 도구 결과, 4096/32768 컨텍스트, 인용·역슬래시·제어 문자·한글의 연속 UTF-8 구간, 가짜 헤더 구분자, 요청/출력 여유, 구간별 재시도, 턴·시간 중단, Ready 체크포인트와 원문 전체 바이트 보존을 검사한다. 이 검사는 로컬 provider fixture 근거이며 실제 모델의 의미 보존 품질을 입증하지 않는다.

변경 후 전체235개 테스트와 Clippy가 통과했다. 실제 CLIProxyAPI 엔드포인트에 gpt-6.1-sol(low)를 요청한 문서 추출 검증도 완료했다. 32768 한도에서 12개 문서(125703바이트)를 각 한 번씩 읽고, 3개 구간 요약 뒤 압축 한 회를 설치하고 5턴·106.6초에 정상 종료했다. 반환한 표식12개를 원문과 검증했으며 원문 아카이브를 보존했다. 수정 전 동일 크기 작업은 첫 도구 묶음 뒤 중단했다. 실행 스크립트는 examples/cliproxy_sol_low_smoke.py다. 이 결과는 해당 문서 작업의 완료와 표식 보존을 확인하며 취약점 탐지 품질이나 프록시 내부 라우팅을 독립적으로 입증하지 않는다.

이전 모델 예산·요약 재시도 변경에서는 전체226개 테스트, Clippy, 포맷 검사가 통과했다. 자동 예산 계산·배포별 한도·완결된 도구 묶음 보존·기존 설정 호환성, 큰 모델의 조기 압축 방지, 앱 지정 한도의 우선순위, 압축 불가능한 큰 요청과 예산을 초과한 요약 결과의 모델 전달 차단을 검사했다. 누적 색인의 재개·실제 검색어 위치·UTF-8 힌트·목록 페이지·도구 인자의 URL·초대형 도구 이름 처리와, 실제 Dust 프로세스의 목록 조회→검색→원문 읽기 흐름도 검사했다. 요약 빈 응답·9,831바이트 상한을 넘는 한글 응답의 복구, 재시도 소진·비활성화·제공자 오류 구분·턴/시간 예산·도구 재실행 방지·이전 색인 보존·아카이브 삭제 후 진단 유지와 실제 Dust 프로세스의 요약 재시도도 검사했다. 실제 Dust 프로세스와 로컬 모델/MCP fixture로100KB 도구 결과의 전문 저장,64KB 이후 원문 검색·조회, 요약 실패 시 보존, 기본 정책의 큰 결과 처리, ACP 세션 격리를 확인했다. 구형 체크포인트의 새 필드 누락도 재개 테스트로 확인했다.

초기 고정 임계값 정책에서는 실제 Codex 모델로 긴 입력3개를 같은 ACP 세션에 보내 모두 end_turn으로 완료했다. 이 과정에서 compact 응답1개가 아카이브에 남았고, 세 입력의 전문이 그대로 보존됨을 확인했다. 모든 모델의 정확한 토큰 계산이나 장기 작업 품질을 입증하는 테스트는 아니다.
