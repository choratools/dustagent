# stdio MCP의 파일시스템 루트 제한

Dust 코어는 호스트에 두고, 파일에 접근하는 stdio MCP 서버마다 준비된 chroot 루트를 지정한다. 설정을 생략한 서버의 기존 실행 방식은 유지한다. 현재 연결 어댑터는 stdio이며 HTTP MCP나 공유 중계기를 추가하는 기능은 아니다.

```json
{
  "mcp_servers": {
    "files": {
      "command": "/usr/bin/node",
      "args": ["/mcp/server.js", "/workspace"],
      "chroot": {
        "root": "/srv/dust-jails/files",
        "user": "1000:1000"
      },
      "env": {
        "HOME": "/tmp",
        "PATH": "/usr/bin:/bin"
      }
    }
  }
}
```

## 준비할 것

`root`는 호스트의 기존 절대 경로이고 `/` 자체는 허용하지 않는다. `command`는 chroot 내부의 절대 경로다. 예제의 `/usr/bin/node`는 호스트의 `/srv/dust-jails/files/usr/bin/node`에 해당한다. 서버 인자와 명시적 환경변수도 내부 경로를 사용한다. 작업 디렉터리는 항상 내부 `/`이며 앱의 호스트 작업 경로를 전달하지 않는다.

운영자가 루트 안에 런타임, 동적 로더·라이브러리, 서버 코드, `node_modules`와 필요한 설정을 준비한다. 외부를 가리키는 심볼릭 링크는 호스트 파일을 가져오는 방법이 아니다. Node의 네이티브 모듈, pnpm 의존성, 브라우저와 npm 캐시도 사용한다면 내부에서 해석 가능한 경로에 있어야 한다. `npx`의 자동 다운로드를 전제로 하지 않는 구성이 권장된다.

작업 파일은 내부 `/workspace` 등에 준비한다. 호스트 파일을 bind mount로 제공하려면 운영자가 실행 전에 구성하고 종료 후 정리해야 한다. 읽기 전용 여부는 마운트와 파일 권한으로 정한다. Dust가 마운트하거나 호스트 권한을 변경하지 않는다. 루트 및 실행 코드의 소유권은 신뢰할 수 있는 운영자가 관리하고, 서버에는 필요한 작업 경로만 쓰기 권한을 준다.

## 실행과 실패

Linux의 GNU `chroot` 실행 파일을 사용한다. 실행기는 루트를 변경할 권한이 필요하다. Dust는 `sudo`를 호출하거나 권한을 자동으로 얻지 않는다. 일반 사용자에게 필요한 권한이 없다면 시작 실패가 정상적인 결과다.

`user`는 0이 아닌 숫자 UID:GID이며 서버 실행 전에 해당 권한으로 전환한다. 보조 그룹은 비운다. 호스트 환경변수를 상속하지 않고 `env`에 명시한 값만 전달한다. 따라서 모델 인증정보나 호스트 PATH가 자동으로 MCP에 넘어가지 않는다. 운영자가 `env`에 넣은 값은 서버에 전달되므로 비밀을 넣을지는 별도로 결정한다. 호스트 chroot 실행기의 로더를 변경할 수 있는 `LD_*`, `GLIBC_TUNABLES`, `GCONV_PATH`, `LOCPATH`, `NLSPATH`는 허용하지 않는다.

실행에 사용하는 GNU 동작과 옵션은 [chroot 공식 문서](https://www.gnu.org/software/coreutils/manual/html_node/chroot-invocation.html)에 설명돼 있다.

명시적 `env`는 호스트 chroot 실행기를 거쳐 서버에 전달된다. 실행기 자체에도 적용되므로 위의 로더 관련 환경변수 제한은 루트 변경 전 단계에도 필요하다.

필요한 실행 파일·라이브러리가 없거나, 권한이 없거나, MCP 초기화가 실패하거나 제한 시간을 넘으면 앱 초기화를 중단한다. chroot를 제거하고 호스트에서 다시 실행하지 않는다. 재시작과 재개에서도 매니페스트의 설정을 사용한다. ACP 세션도 앱에 선언된 서버 설정으로 실행한다.

## 경계

이 기능은 설정된 MCP 프로세스와 그 자식의 파일 경로 해석 범위를 줄인다. 네트워크·프로세스 네임스페이스나 자원 할당 격리 기능은 아니다. 권한 상승 파일, 장치, 호스트 소켓, `/proc` 등을 제공하면 접근 경계가 넓어질 수 있으므로 준비된 루트의 내용도 검토해야 한다.

Dust 본체, native 도구, validation checker, 패치 명령은 이 chroot 밖에서 실행한다. 다른 파일 접근 MCP도 제한하려면 해당 서버에 각각 설정해야 한다. 앱 전체가 격리됐다는 의미는 아니다. 패키지 배포 시 chroot 경로는 대상 호스트에서 별도로 준비해야 한다.

## 검증

설정 검사, 기존 매니페스트 직렬화 호환성, 필요한 서버의 시작 실패를 테스트한다. 실제 chroot 테스트는 정적 BusyBox로 만든 임시 루트에서 stdio MCP 응답을 받아 UID/GID, 보조 그룹, 작업 경로, 환경변수 및 호스트 파일·외부 심볼릭 링크의 비노출을 확인한다.

개발 호스트에서는 chroot 권한 부족 시 중단하는 경로를 확인했다. 같은 테스트 바이너리를 네트워크 없는 로컬 Docker 컨테이너에서 실행해 실제 chroot 성공 경로도 확인했다. 컨테이너에는 테스트 바이너리와 정적 BusyBox만 읽기 전용으로 제공하고 임시 루트는 tmpfs에 만들었다. Node 기반 실제 MCP와 브라우저 런타임은 이 검증 범위에 포함하지 않는다.
