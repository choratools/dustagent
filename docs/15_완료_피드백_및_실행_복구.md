# 완료 피드백과 실행 복구

코어는 앱의 완료 검사 결과를 전달하고 오류를 복구하며 메모를 보존한다. 탐색 단계나 다음 행동은 고정하지 않는다. 별도 감독 LLM도 호출하지 않는다.

## 완료 검사 계약

validation.mode는 기본 legacy다. 기존 검사기의 stdin은 정확히 input/output 쌍이고 stdout은 passed/reason이다. legacy 직렬화 필드는 생략해 기존 매니페스트와 체크포인트의 해시를 유지한다.

feedback 모드는 실행의 최종 응답 후보가 나온 뒤 호출한다. stdin 예시는 다음과 같다.

```json
{
  "input": "본문을 확보",
  "output": "제목과 링크를 찾았습니다",
  "tool_calls": [],
  "state": {"revision": 0, "entries": {}}
}
```

stdout 계약은 다음과 같다.

```json
{"decision":"continue","reason":"본문을 확인한 도구 증거가 없습니다"}
```

complete는 완료, continue는 보완 필요, blocked는 미완료 종료다. 검사 프로세스는 정상 종료 코드와 정확한 JSON 판정을 반환해야 한다. 이유는 비어 있지 않은 최대 2048바이트다. 비정상 종료·프로세스 시작 실패·출력 초과·잘못된 판정·검사 시간초과는 계속 실행하지 않는다. 검사 출력 상한은 기존 8192바이트를 유지한다.

검사기에 실제 기록된 tool_calls를 전달한다. 기록은 전체 원본이라는 보장이 없으며 truncated를 확인해야 한다. 메모나 모델 주장을 실제 증거로 해석하지 않는 것은 앱 검사기의 책임이다. 증거 파일 검사가 필요하면 명시된 검사기가 도구 결과의 참조를 검증해서 읽는다. 코어가 임의 증거 파일을 자동 탐색하지 않는다.

continue면 응답 후보 다음에 사용자 역할의 검사 피드백을 추가하고 다음 모델 턴을 실행한다. 피드백은 부족한 조건을 설명하며 모델이 행동을 선택한다. 같은 턴·시간 예산을 쓰므로 무한 반복하지 않는다. 턴이 없으면 turn_limit이며 마지막 후보와 판정은 보고서에 남는다.

검사 직전 ValidationInFlight를 저장한다. 결과가 continue이면 피드백을 포함한 Ready 상태를 저장한 뒤 다음 요청을 보낸다. 중단된 검사는 재개할 수 없으며, 확인된 피드백은 재개할 수 있다. validation_history는 각 후보의 턴과 판정, validation은 가장 최근 판정이다.

`${DUST_APP_ROOT}`를 검사기 command/args에 쓰면 실행 시 현재 패키지 루트로 치환한다. 매니페스트 자체는 수정하지 않아 내용 해시와 체크포인트 바인딩을 유지한다. 단일 매니페스트 로딩에서는 연결한 앱 루트가 기준이다. 일반 상대 경로와 MCP 명령 경로는 기존처럼 작업 디렉터리 기준이다.

경험 조사에 쓰는 validate 함수는 input/output 쌍 계약을 유지한다. feedback 모드 검사기라도 continue는 재사용 통과로 보지 않으며 조사 루프를 자동으로 이어가지 않는다. 도구 증거가 필수인 검사기는 이 쌍 입력만으로 통과할 수 없으므로 성공 사례 재사용을 거부할 수 있다.

## 모델 요청 재시도

Provider 오류를 transient/permanent/invalid_response로 구분한다. 실행 루프에서 transient만 재시도한다. 기본 정책은 max_retries=5, base_delay_ms=1000이다. 추가 요청 전에 1,2,4,8,10초 대기하며 기존 전체 예산이 우선한다. Provider가 HTTP 429 등 재시도 가능한 응답에 `Retry-After`를 보내면 초 단위 값 또는 HTTP 날짜를 읽고, 지수 대기보다 길 때 그 값을 최소 대기로 사용한다. 대기는 남은 실행 시간 예산을 넘지 않는다.

```json
{"provider_retry":{"max_retries":5,"base_delay_ms":1000}}
```

최대 재시도는 5회, 기본 대기는 1~10000ms, 지수 대기는 최대 10초다. 0회로 끌 수 있다. 인증·일반 요청 오류·JSON 구문 오류·응답 구조 오류는 재시도하지 않는다. 연결·요청 시간초과·응답 본문 전송 실패와 HTTP408/429/500/502/503/504가 일시 오류다. `Retry-After`가 없는 경우 점진 대기를 적용한다. 기존 사용자 정의 Provider의 Llm 문자열 오류는 분류 정보가 없으므로 재시도하지 않는다.

재시도는 응답을 수락하기 전 같은 메시지·도구 정의로 요청한다. 요청 시도는 동일 모델 턴 안에서 제한하며 provider_retries에 턴·재시도 번호·오류·실제 대기 시간을 남긴다. 추가 추론 비용이 발생할 수 있다. new·독립 경험 검토는 이 실행 루프 재시도 정책에 포함되지 않는다. 완료한 도구나 실행 결과가 불확실한 도구를 재실행하지 않는다.

## 실행별 작업 메모

working_state=true인 앱에만 다음 도구를 제공한다.

```text
dustagent__state_get(key)
dustagent__state_put(key,value)
dustagent__state_list(prefix?,cursor?)
```

메모는 revision과 entries를 가진 JSON이다. get은 found/value/revision, put은 revision을 반환한다. list는 사전순으로 최대20개 key와 next_cursor를 반환하며 해당 cursor 다음부터 이어 읽는다. 앱이나 모델이 자유롭게 키 구조를 정한다. 실패 시 isError 응답을 반환하고 기존 상태를 변경하지 않는다.

키는 비어 있지 않은 최대256문자이며 NUL을 허용하지 않는다. 값은 JSON 인코딩 최대16KiB, 전체 상태는 최대256KiB, 항목은256개다. revision 증가가 overflow하면 쓰기를 거부한다. 새 실행은 빈 상태에서 시작하고 재개는 체크포인트 상태를 복원한다. 보고서의 working_state는 마지막 상태다. 별도 파일 접근이나 상태 전용 서버를 추가하지 않는다.

메모는 관찰 증거와 다르다. evidence_call_id 같은 참조를 저장할 수 있으나 검사기는 실제 도구 기록과 대조해야 한다. 코어는 메모를 해석해 작업 순서를 정하지 않는다.

## 검증과 비용

로컬 HTTP 모의 서버는 재시도 가능한 상태코드와 인증 오류·잘못된 응답·본문 전송 중단을 구분한다. 실행 테스트는 동일 대화 재요청, 제한·대기 시간 소진, 도구 중복 실행 방지, 실제 Python 검사기의 continue/complete/blocked, 피드백·상태 체크포인트 재개를 확인한다. 서로 다른 패키지 추출 경로에서도 포함된 검사기가 실행되는 것을 확인한다.

정상 모델 응답에는 재시도 대기가 추가되지 않는다. 검사와 작업 메모는 앱의 명시적 설정이며, 검사 피드백으로 추가 모델 턴이 필요하면 작업 시간과 비용이 늘어난다. 실제 모델의 탐색 품질 개선이나 브라우저 작업 복구율은 아직 측정하지 않았다.
